# 步骤2：分类体系设计（ABCDE 方法论）与预生成

用户可以完全自定义类目；若用户没有现成方案，用本方法论**根据抓到的列表自动生成提案**。
核心思想：六个维度（A 状态 / B 系列 / C 类型 / D 厂商 / E 其他 / F 特性）互不重叠，一款游戏可同时
属于 B/C/D/F 的多个小类，A 互斥，E 处理非游戏内容。

## 维度定义

| 维度 | 含义 | 互斥性 | 谁能进 |
|---|---|---|---|
| A 状态 | 用户个人的游玩状态 | **互斥**，仅一个 | 仅 installed=true 的游戏；工具/软件不进 A |
| B 系列 | 作品系列/IP（如某长跑系列的历代作） | 可多选 | 名称/事实属于该系列 |
| C 类型 | **玩法类型**（怎么玩） | 可多选（建议 1–3 个） | 全部游戏 |
| D 厂商 | 开发商/发行商 | 可多选 | 全部游戏；涉及几家标几家 |
| E 其他 | 非游戏内容 | 可多选 | 工具软件/原声带/画集视频等 |
| F 特性 | **属性**（能不能/怎么一起玩、支持什么） | 可多选 | 全部游戏 |

> **C 类型 vs F 特性**：描述"玩法是什么"→ C；描述"是否/如何一起玩、支持什么"→ F。
> 「多人合作」常被塞进 C，但它**是属性**——放 F 后 C 维度不再被污染。
> 真实案例：把 `C19 多人合作` 迁成 `F01 特性-多人合作`（257 款）后，动作类与其他类型的重叠明显下降。

## 预生成流程（按抓到的列表统计，不要凭空造）

1. **A 状态**：询问用户或按游玩时间分布提案。典型四档：正在玩 / 计划玩 / 长线常驻 / 暂时搁置。
   用户逐款指定或由用户确认 agent 提案；不在分配表中的已安装游戏给默认档并在输出中提示。
2. **B 系列**：对全部游戏名做前缀/关键词聚类（同一 IP 常有可识别命名模式），再叠加
   agent 自身对知名系列的常识。**规模 ≥2 款才立类**；只有 1 款的 IP 不立类。
3. **C 类型**：先列一版通用玩法类型（视觉小说/角色扮演/策略/动作/模拟经营/解谜/恐怖/
   悬疑推理/开放世界/Roguelike/卡牌/放置/休闲/叙事冒险/魂类/工具/软件 …），
   再按列表统计删掉没有成员的、拆开成员过多的。**一款建议 1–3 个**——别挂成 4-5 个
   （泛化类互吸的典型症状，见 `references/category-quality.md`）。
   **注意**：像「多人合作」「支持手柄」「VR」这类是**属性**，应放 F 而不是 C。
4. **D 厂商**：知名大厂（作品 ≥3 或全球知名）单独成类；其余全部进兜底类"其他/小厂/独立"。
   用元数据里的 developer/publisher 字段统计频次来选大厂。
   **兜底类可再细化**（见 `references/vendor-region.md`）：联网判厂商**国别**（把中国厂商单列，
   命中归 D21）＋把**名厂逐个独立成类**，长尾才留在兜底。
5. **E 其他**：工具软件/音频 OST/视频画集/其他，按元数据 type 字段（application/music/video）。
6. **F 特性（可选）**：把"属性"立类——多人合作、本地同屏、VR、支持手柄、成就、云存档等。
   用量/标签或用户偏好决定启用哪些；启用时给 `preclassification.csv` 增加 `F_tags` 列
   （`build_collections.py` 已支持 `F -> F_tags`）。
7. 与用户确认提案后固化为 `categories.md`（类目定义唯一源头）。

## 编号规范（重要，避免返工）

- 每个大类内小类用两位数字编号：`A01`、`B07`、`C12`、`D42`、`E01`、`F01`
- **兜底类（"其他"）编号必须是大类内最大号**且与主编号留出空档（如 D 类主编号到 D64，
  兜底用 D99）——保证任何排序下兜底类都在最后，且未来插入新类不需要重编号
- 中间编号保持**连续无空位**；删除类目时要么重编号，要么新类目复用空位
- 收藏集名称即 `<编码> <大类名>-<小类名>`（如 `C06 模拟经营`），写入 Steam 后用户按名称排序自然分组

## 类目定义文档模板（categories.md）

```markdown
# 分类类目定义  版本 1.0
## A 状态（N 类，仅已安装，互斥）
- A01 状态-正在玩    规则: ...
## B 系列（N 类，可多选）
- B01 系列-XXX       关键词: ...
## C 类型（N 类，可多选 2-5 个）
- C01 类型-视觉小说  判定: 标签 Visual Novel / 名称模式 ...
## D 厂商（主编号 N 类 + D99 兜底）
- D01 厂商-XXX       匹配: developer/publisher 含 ...
- D99 厂商-其他/小厂/独立/待确认   规则: 未命中任何 D 类时归入
## E 其他（N 类）
- E01 其他-工具软件
## 补充规则
- 工具软件不进 A 状态；每款游戏 C 至少 1 个，无法确定进待确认表
```

## 预分类执行

两种方式（可混合）：

**规则式**：为 B/C/D 各写关键词/正则映射（存 `rules.json`：B_keywords、C_patterns、
D_patterns、tag_to_c），脚本对每款游戏取并集打码。优点快、可重复；缺点 Steam 标签
泛滥导致虚胖（这正是步骤3存在的意义）。元数据来源见 `methods-review.md`。

**LLM 式**：把列表按 25-50 款一批交给 LLM，附类目定义，输出统一 CSV。
列格式与最终表一致：`appid,name,installed,A_status,B_series,C_types,D_vendors,E_other,是否确定`。

无论哪种：无法确定 C 的进待确认表（`pending_confirmation.csv`），不留空。

## 产出与汇报

- `categories.md` + `preclassification.csv`（+ 待确认表）
- 汇报：各类目数量、每个类目 2-3 个代表成员、待确认数量 → **等用户确认类目与预分类**
